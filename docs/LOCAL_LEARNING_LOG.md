# 本地接入学习记录

日期：2026-11-01。只记录可迁移的研究和实现，不记录用户姓名、生日、命盘或账号凭据。

## 1. 最开始的理解不完整

第一次只阅读了快速开始和 API 缺失说明，跑通排盘后就交付。这没有达到用户要“本地体验解读”的目标。

后续发现 README 的 v4 数据集章节：断语库代码未开源，但其生成的 **13 主题本命全文**作为 Release 开源。Demo 的 `db-analysis.ts` 为空和 `/api/interpret` 缺失，不等于无法本地读取作者的本命解读。

实现决策：连接 Release 的年份压缩文件，避免先建数据库、先找 Key 或下载/解压 56.6 GB。

## 2. 解读数据和 AI 不是一件事

本命 v4 数据集是排盘引擎＋断语库确定性生成，覆盖 1950–2026 的生日组合。`c` 字段提供 13 个主题全文。它不是只含标签或排盘 JSON，也不包含完整 AI 追问能力。

必须精确匹配 `y/m/d/h/g`，不以相似命盘代替；`h` 是时辰序号。数据正文按旧 XD2 亮度口径生成，本地排盘对齐 XD2。

## 3. 流年初版为什么不够

初版用太岁落本命宫、年干四化、所属大限组合几段解释。它可以解释盘面，却没有完成本命全文级别的综合解读。

用户明确指出：流年缺少具体分析，需要同等质量。不能通过拉长套话或重排本命段落来冒充深度。

## 5. 深度流年需要什么

当前已经准备的模型输入：

- 本命十二宫星曜、亮度、本命四化、命身宫、五行局。
- 原作者 13 主题本命全文，作为终身底层语义资料。
- 选年实际大限及其三方四正；小限落宫和对宫。
- 2026–2031 六年上下文，识别换大限与逐年差异。
- 可点击核对的课程原话，以及稳定事实 ID。

报告要求：年度总论、事业学习、财运资源、感情合作、身心节律、家庭迁移。每个主题都要解释“哪些本命底色＋什么大限背景＋什么当年信号”支持判断；同时写反向证据与不足。没有当年信号就写没有，不能为了填满章节而虚构。

内容质量门槛：不同年有实际不同的证据链；相同信号不硬凑差异；小限/本命/大限不混标；不编引文；不能把流年分析包装成经验证实的未来预测。

## 6. 工程中发现的 UI 问题

原 `/chart` 和 `ChartBoard` 各有独立年份状态，外层切年不更新内层。已改为受控年份并去掉重复导航。选未来年时大限高亮也必须重算，不能继续高亮现实当前大限。

## 7. AI 接入及实测

用户已明确授权：综合运用现有 AI，把开源项目作为 base 强化，最终要能回答其提出的问题。已复用本机 Codex ChatGPT 登录，CLI 正规调用，不读取 OAuth 文件、不提取令牌。默认采用现有 `gpt-6.1-sol`，禁用 shell 工具和用户插件配置，独立临时目录、只读沙箱。

本机直连超时，已有代理可用，故只配置项目 `.env.local` 的 `ZIWEI_CODEX_PROXY`，不改系统设置。任务显式点击触发，后台排队、去重和轮询，完成后缓存本机，不进 Git。

已真实生成并人工完整审阅：

- 虚构生日的 2031 年六主题报告（约3400字符），能解释新大限、大小限关系、支持与限制，还发现原始本命断语与实际星位表述不一致之处，并以计算值为准。
- 界面选2026，问题问2027与2031事业对比。回答使用对应年份，指出同一宫位从小限辅助上升为大限背景后的权重变化，没有把2026套给所有年份。
- 回答会区分终身特征、当年信号及现实信息不足；列出引用 ID，页面可展开对应星曜与课程来源。
- 真实多轮追问：在上述两年对比后补充“假设是产品经理，希望由个人贡献转向带团队”。回答能承接前文年份，给出授权试点、带教、管理证据及资源取舍方面的具体行动，没有把命盘当成管理能力已成立的证明。
- 网页实际验证修复了 Next dev 将内部 URL 规范成 localhost、浏览器使用 127.0.0.1 引发的来源校验问题。仍拒绝无关来源；报告与问答均经桌面和390px手机端验证。

这些验证说明能输出有依据的综合解释，**不能证明命理能够准确预测未来**。结构/引用自动检查也不能代替内容审阅。后续持续评估重点：追问承接、年份选择、流派不混用、证据冲突、没有证据时明确承认，以及现实问题回答是否具体。

### 找到并修正的四处原作接入问题

1. **样式变量断层**：原组件大量引用 `--t-gold/--t-border/--t-card/--t-text` 等10个旧变量；原 globals.css 只有新设计系统 `--ac/--tx-*/--bg-*/--bdr`，没有旧变量定义。浏览器实测旧变量为空。现把它们映射回作者已有新Token，补齐原组件 `card-glass/card-inner` 的卡片样式；没有另创配色。
2. **星曜点击未接入**：此前 `ChartBoard.onStarSelect` 没有传入，原有332行 `StarDetailPanel` 从未出现在我们的流程。现使用原组件，显示关键词和原始资料，且明确不是个性化流年结论；旧资料可能与新版断语存在差异，不能不加核对地当作新增权威事实。
3. **格局引擎未充分使用**：原 `detectPatterns/getMingGongSummary` 是可复用资产。它们有server-only边界，不能直接把旧client ChartSummary强行导入。现由本命读取接口在服务端调用原函数，页面显示原命格概览、原格局成立条件/限制与出处，原13主题文字不变。
4. **原内容入口被弱化**：接回原首页、古籍库、主星概览与主题切换入口。AI增强保留在可展开区域，不再作为替代原作的默认主阅读。

验证：类型检查通过，原768盘及所有附属回归全过；浏览器验证原星曜点击/关闭、命格与格局、13主题原文、暗亮主题、古籍入口、390px手机布局和可选AI展开，均通过。没有为本轮复核额外生成新的AI报告。

### 不能被这轮修复掩盖的待办

- [作者 #17 的方法](https://github.com/Renhuai123/ziwei-doushu/issues/17)：每个大限、流年等层的完整十二宫地支映射应先由代码计算，再整表给AI。目前我们的上下文有本命十二宫、所选大限、三方和小限，但尚未达到作者所说的“所有大限/所有层完整映射表”覆盖；后续须按原引擎补齐并验证，不让模型代算。
- #45 指出 `true-solar-time.ts` 与表单内简化经度校正未统一，`generateChart`并不直接消化longitude。校正、晚子换日和海外时区必须逐入口核验；本轮没有擅改排盘口径。现有回归通过不等于所有表单边界已验完。
- 不把作者在线版视觉称为已复刻。当前修的是原作已有资产的接线和显示；完整线上效果对照仍须实际进入其新版页面或取得用户具体参考。

新的交付原则：先明确作者的内容层、算法层、展示层和未发布边界；先将可用的原文、原组件、原工具正确接入并做原版对照，再决定AI增强需要补哪一层。不能以一份通顺的AI长文或功能按钮通过测试，宣称已充分利用原作。
